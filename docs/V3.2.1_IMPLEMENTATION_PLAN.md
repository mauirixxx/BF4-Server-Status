# BF4 Server Watcher v3.2.1 — implementation and validation plan

Status: **in development**. Single feature branch: `feature/v3.2.1-stabilization`. Base: `main` (v3.2.0). Production stays on v3.2.0 until validation and approval.

## Release scope

1. Repair `/status server` with player roster enabled, preserving Mobile and Wide layouts. Test both layouts with empty, short and long rosters, disabled roster, and missing server data.
2. Improve failed-command audit records so the attempted target is identifiable without logging secrets or private message content.
3. Add structured database connectivity lifecycle logging: first failure, rate-limited continuing outage/retry, restoration and duration. Scope state by worker and subsystem. Preserve existing SQLAlchemy pool pre-ping, retry behavior, scheduling, ownership fencing and Keeper request budgets. Avoid treating a successful TCP connection alone as proof that the workload recovered.
4. Prevent repetitive Discord 403 Missing Access log storms. Do not silently disable guilds or channels; preserve user configuration, distinguish permanent permission failures from transient API failures, and log enough destination context for diagnosis.
5. Regression coverage for all changes and existing distributed behavior.

## Observations motivating this release

- During October 24 Honolulu cable-modem interruption, workers hnl-01/02/03 logged database/DNS failures and later completed Keeper sweeps successfully without Docker restarts.
- An administrator-initiated PostgreSQL restart produced expected AdminShutdown errors across the fleet.
- Guild 1539467992377720855 (The Hog Pit) has not completed bot configuration; errors for inaccessible channel 1558730926781894706 should not overwhelm logs. Do not change its configuration without explicit authorization.
- Ten BF4SW v3.2.0 containers were observed running with zero Docker restart counts; this is not proof of zero collection gaps.

## Development and rollout rules

- **All code, documentation, tests and test fixes stay on this one feature branch.** No secondary test branches, no commits to `main` until approved merge.
- Before code changes, inspect existing implementation, tests, command docs and database schema. Verify live schema before any migration or query changes; prefer no schema migration for this release.
- Do not edit production deployment files in place or restart production workers for development.
- Validate unit tests, integration behavior, both status layouts, reconnection transitions, repeated failure suppression and distributed lease/pacing invariants.
- Test a single isolated worker/candidate first, then staged fleet rollout only with approval and rollback instructions.
- Update relevant existing `COMMANDS.md`, `README.md`, `CHANGELOG.md`, release notes and design documentation to reflect *implemented* behavior, not proposed behavior. Maintain this plan as work progresses.

## Out of scope unless separately approved

GUID lookup and historical names; Battlelog URL capture; unrelated dashboard work; changes to collection rate limits, leader election or production guild settings.

## Acceptance criteria

- Mobile and Wide `/status server` renders work with and without players.
- Audit failures identify the attempted target.
- Connection loss and restoration appear once per transition; ongoing outage logging is bounded; outage duration is accurate; independent subsystems are distinguishable.
- Discord permission failures remain diagnosable without repeated high-volume errors or unwanted configuration mutation.
- Tests pass and evidence is recorded here before release.

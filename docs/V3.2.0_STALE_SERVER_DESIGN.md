# BF4 Server Watcher v3.2.0 — Stale Server Lifecycle Design

Status: design baseline / implementation checklist

This document records the agreed v3.2.0 server-catalog, lifecycle, discovery, Discord, presence, and rollout semantics before implementation begins.

## Core principles

- `bf4_servers` is the permanent global BF4 server catalog. Once a GUID enters the catalog, routine application behavior does not delete it.
- A GUID is the durable server identity. Server names are mutable metadata.
- Keeper is the ultimate source of truth for whether a server currently exists and for its canonical current name.
- BFLIST is PC discovery only. Absence from BFLIST has no lifecycle meaning.
- `/addserver` can add/reaffirm a guild relationship and request immediate Keeper verification, but cannot itself declare a server online/CONFIRMED.
- `/delserver` removes only that guild's relationship/favorite. It never removes the server from the global catalog.
- Lifecycle and Keeper priority lanes are independent concepts.

## Lifecycle states

States:

- `DISCOVERED` — newly admitted GUID awaiting a meaningful Keeper result.
- `CONFIRMED` — Keeper has positively returned valid expected BF4 server data.
- `GRACE` — at least one definitive Keeper 404 has been observed; normal polling continues temporarily.
- `STALE` — the 404 condition has persisted beyond the 60-minute grace period; normal fast/bulk polling stops and lifecycle probes are used.
- `RETIRED` — the server has remained definitively unavailable for at least 72 hours from the first 404 and is removed from routine polling.

Normal outage path:

`CONFIRMED -> GRACE -> STALE -> RETIRED`

Admission path:

`BFLIST or new /addserver -> DISCOVERED -> Keeper SUCCESS -> CONFIRMED`

`DISCOVERED -> Keeper 404 -> GRACE`

Any valid Keeper success from `GRACE`, `STALE`, or `RETIRED` immediately returns the server to `CONFIRMED`.

## Keeper result classification

Keeper results must be classified centrally:

- `SUCCESS`: HTTP/API response is valid and contains the expected BF4 snapshot structure.
- `NOT_FOUND`: definitive server-specific Keeper 404.
- `ERROR`: timeout, connection failure, 403, 429, 5xx, malformed JSON, missing/invalid snapshot, unexpected response, or other non-authoritative failure.

Only `SUCCESS` and `NOT_FOUND` carry lifecycle meaning.

`ERROR` does not advance, reset, or otherwise mutate the server lifecycle.

A dictionary-shaped snapshot alone is not sufficient. v3.2.0 must define a conservative `validate_keeper_snapshot()` based on stable fields present in real PC/Xbox/PlayStation snapshots. Partial/malformed 200 responses are `ERROR`, not success and not 404 evidence.

## Timing policy

- Grace period: 60 minutes from the first definitive Keeper 404.
- `first_404_at` is set at the time the first definitive 404 is observed and is never reset by subsequent 404s.
- During GRACE, the server remains on its normal fast/bulk cadence.
- After GRACE, STALE servers receive approximately hourly lifecycle probes.
- Retirement threshold: 72 hours from `first_404_at`.
- Reaching 72 hours by wall clock is not sufficient to retire a server. A definitive 404 at/after the threshold is required. If Keeper is failing generically, the server remains STALE.
- RETIRED PC servers receive no scheduled resurrection probe.
- RETIRED Xbox/PlayStation servers receive approximately one resurrection probe every 7x24 hours.
- Any successful Keeper response immediately restores `CONFIRMED` and normal scheduling.

## Proposed `bf4_servers` lifecycle fields

Add:

- `lifecycle_state`
- `first_404_at`
- `last_keeper_success_at`
- `last_keeper_result_at`
- `retired_at`
- `next_lifecycle_probe_at`

Useful indexes:

- `lifecycle_state`
- `(lifecycle_state, next_lifecycle_probe_at)`

No persistent consecutive-404 counter is required; policy is time-based.

`last_keeper_result_at` protects against out-of-order distributed results. It represents the observation/request timestamp used for ordering, not merely DB commit time. A lifecycle mutation from an observation older than the current `last_keeper_result_at` is ignored.

Lifecycle transitions must lock/re-evaluate the current `bf4_servers` row transactionally (for example `SELECT ... FOR UPDATE`) so worker failover/races are harmless.

## v3.2.0 migration bootstrap

All existing `bf4_servers` rows start a new lifecycle as `CONFIRMED`.

Migration/bootstrap values:

- `lifecycle_state = CONFIRMED`
- `first_404_at = NULL`
- `retired_at = NULL`
- `next_lifecycle_probe_at = NULL`
- `last_keeper_success_at` = latest existing `keeper_snapshots.fetched_at` for the GUID where available; otherwise NULL
- `last_keeper_result_at` initialized conservatively from available Keeper evidence where appropriate

The deployment intentionally causes all existing global catalog servers to become eligible for the new lifecycle system. This allows v3.2.0 to clean the historical catalog naturally through Keeper evidence.

## Canonical names and name history

GUID is permanent identity. Keeper owns the canonical current server name.

BFLIST may provide a discovery/debug name but may not overwrite a Keeper-established canonical name.

Add `bf4_server_name_history` with conceptually:

- `id`
- `server_guid`
- `server_name`
- `first_seen_at`
- `last_seen_at`

Only actual name periods/transitions are stored, not one row per Keeper observation.

On Keeper success:

- same name: no name-history transition;
- changed name: close the previous period, update `bf4_servers.server_name`, create the new current history period.

Existing names are seeded into name history at v3.2.0 migration/initialization without pretending the system knows an earlier first-seen time that was never recorded.

## Keeper scheduling universe

Pre-v3.2.0, `guild_servers` effectively defines the Keeper polling universe. v3.2.0 changes this: `bf4_servers` is the master Keeper catalog.

Normal lanes:

- `CONFIRMED` + guild-default priority => FAST
- `CONFIRMED` otherwise => BULK
- `DISCOVERED` => BULK until Keeper gives a meaningful result
- `GRACE` retains the normal FAST/BULK priority it would otherwise have

Lifecycle probes:

- `STALE` leaves normal FAST/BULK scheduling and is eligible only when `next_lifecycle_probe_at <= NOW()`.
- `RETIRED` PC: no routine Keeper work.
- `RETIRED` Xbox/PlayStation: eligible for a lifecycle probe when due, approximately every 7 days.

Lifecycle probes use the existing Keeper workers, distributed ownership/fencing philosophy, and PostgreSQL cluster rate gate. No new Keeper worker role is required.

A last guild association being removed does not stop global bulk monitoring of a CONFIRMED server.

## `/addserver` semantics

`/addserver` remains management-controlled.

Brand-new GUID:

- create the global catalog row as `DISCOVERED`;
- create/reaffirm the guild relationship;
- request Keeper verification through protected scheduling/rate-gate behavior;
- Keeper success => CONFIRMED;
- Keeper 404 => GRACE with `first_404_at` set;
- Keeper ERROR => remain DISCOVERED.

Existing CONFIRMED GUID:

- create the guild relationship if missing;
- do not reset lifecycle timestamps merely because `/addserver` ran.

Existing GRACE/STALE/RETIRED GUID:

- create/reaffirm the guild relationship;
- request immediate Keeper verification;
- only Keeper success can set CONFIRMED;
- 404 preserves/advances the legitimate existing outage according to lifecycle policy;
- generic Keeper error leaves lifecycle unchanged.

If the server is already associated with the guild, `/addserver` is still meaningful for GRACE/STALE/RETIRED because it can request immediate verification. Administrators do not need to `/delserver` then `/addserver`.

Running `/addserver` never resets `first_404_at`. Only actual Keeper success clears the outage clock.

Suggested command feedback distinguishes confirmed success, current Keeper 404/offline state, retired-but-still-offline state, and inability to verify due to Keeper/infrastructure error. Command responses should be ephemeral where appropriate.

## `/delserver` semantics

`/delserver` removes only the current guild's `guild_servers` relationship/favorite, subject to the existing default-server safeguards.

It never deletes the physical server from `bf4_servers`, and never changes global lifecycle/name/player history.

When removing the guild relationship, BF4SW cleans its current persistent Discord state for that guild/server (status, roster, ETA, lifecycle offline notice, temporary recovery notice as applicable). Permanent `/logschannel` lifecycle history is not deleted.

## Discord behavior for STALE / RETIRED / recovery

### STALE

The public/current status channel should not keep indefinitely stale status/roster data.

When `GRACE -> STALE`:

- clean the normal persistent status material owned by BF4SW for that guild/server, including stale roster/ETA/status blocks as appropriate;
- replace it with one persistent offline notice using the guild's watched server name/last known name;
- show the outage start using `first_404_at` as a Discord timestamp;
- if `/setmanagementrole` is configured, ping that management role once when the STALE notice is first created and state that it has been notified;
- do not repeatedly ping on hourly 404 probes.

Example intent:

`This Discord's BF4 server "X Server Name" has been offline since <timestamp>.`

If configured:

`@ManagementRole has been notified.`

### RETIRED

Edit/reuse the existing offline notice rather than posting another public status-channel message. Do not ping management again.

Add wording equivalent to:

`"X Server Name" has been offline for 3 days and is no longer being routinely polled. If the server has been restarted, use /addserver to resume monitoring immediately.`

Do not claim that the guild must re-add a relationship that BF4SW intentionally preserved.

### Recovery

When Keeper successfully restores STALE/RETIRED to CONFIRMED:

- remove the offline notice;
- restore normal status/roster/ETA behavior;
- post one temporary ONLINE/recovery notice;
- leave the ONLINE notice visible until the first subsequent BF4 map change;
- at that first post-recovery map change, delete the temporary ONLINE notice and continue normal map-change behavior.

The temporary recovery notice should therefore remain long enough to be seen without becoming permanent status-channel clutter.

Lifecycle message IDs/state needed for HA reconciliation must be durable (likely in `guild_server_state` or equivalent), not process-local.

## `/logschannel` lifecycle audit

If a guild has `/logschannel` configured, write permanent lifecycle messages there in addition to the current-channel behavior:

- STALE => permanent OFFLINE event
- RETIRED => permanent RETIRED event
- recovery => permanent ONLINE event

Never ping the management role from `/logschannel`.

Log-channel lifecycle messages are historical/audit records and are not automatically cleaned up.

## Rich Presence / live aggregation

Only `CONFIRMED` servers contribute to Rich Presence server and player counts.

Desired presentation:

`Tracking X BF4 Servers | Y Players`

A definitive first 404 immediately changes CONFIRMED to GRACE and therefore removes that server and its cached player count from the live aggregate.

Generic Keeper failures do not change CONFIRMED state. Existing snapshot freshness/resilience behavior remains available when there is no authoritative 404 evidence.

Lifecycle eligibility and snapshot/data-health are separate concepts.

## BFLIST PC discovery

BFLIST has one job: discover previously unknown PC GUIDs.

Daily discovery time is locked to:

- 09:30 HST (`Pacific/Honolulu`)
- 19:30 UTC

This was selected from the existing dashboard population history. The normalized 30-day PC peak was at approximately 09:30 HST, and 7-day/hourly results agreed with the same peak window.

Execution owner: whichever worker currently owns Discord leadership also performs the BFLIST discovery sweep. No separate worker role/election is introduced.

Persist sufficient discovery-run state so a leadership transition around the scheduled time can determine whether that day's successful sweep has already occurred. The operation must be idempotent.

For each BFLIST PC GUID:

- known GUID => ignore completely, regardless of CONFIRMED/GRACE/STALE/RETIRED state;
- unknown GUID => insert into global catalog as DISCOVERED and allow normal protected Keeper verification.

BFLIST does not resurrect known RETIRED servers, refresh lifecycle timestamps, or provide negative evidence.

BFLIST failure/partial invalid data changes no existing server lifecycle state.

Newly discovered servers must not bypass Keeper rate protection or create an uncontrolled request burst.

## Data Quality dashboard semantics (implemented last)

Dashboard work is intentionally the final implementation phase after backend lifecycle behavior has soaked successfully.

Keep the existing Snapshot Health data. Do not replace it.

At the bottom of the existing Data Quality box, add a Server Lifecycle subsection showing conceptually:

- Confirmed Servers
- Grace Servers
- Offline/Stale Servers
- Retired Servers
- Global Catalog

Snapshot `Stale` and lifecycle `STALE` are different concepts and should remain visibly contextualized by their subsection labels.

Live dashboard server/player counts and population-history sampling should ultimately use the same CONFIRMED-only universe as Rich Presence.

## Future / explicitly out of v3.2.0 core scope

Park for later discussion rather than expanding the stale-server implementation:

- Lifecycle operator inspection is designed and locked, but implementation remains deferred until after the core lifecycle/rollout work. Plain `/operator status` keeps its existing behavior and gains only a compact lifecycle count block (CONFIRMED/GRACE/STALE/RETIRED/DISCOVERED/total). An optional lifecycle choice provides state-specific human-readable inspection with fields appropriate to that state and a bounded preview rather than flooding Discord. Full matching results are exported as CSV; an `all` form provides the lifecycle breakdown plus a complete global-catalog CSV. CSV rows use canonical Keeper/global server identity and name, never guild display aliases. This operator export is also intended as an independent validation source for the dashboard.
- Server analytics such as unique players per permanent GUID, lifetime/period player counts, sessions, server-history/detail pages, retention, busiest maps/hours, etc. Existing player-session/persona data likely provides much of the foundation.

## Production deployment strategy

v3.2.0 is a stop-the-world maintenance deployment; mixed v3.1.x/v3.2.0 operation after schema migration is not a requirement.

Planned rollout:

1. Drain all eight BF4SW worker nodes.
2. Stop/shut down BF4SW on all eight nodes and verify none remain active.
3. Take/verify the pre-maintenance PostgreSQL backup/checkpoint and rollback point.
4. Deploy v3.2.0 code to `mak-01` first.
5. Apply the Alembic schema migration with the fleet stopped.
6. Start `mak-01` only.
7. Perform single-node smoke/abuse testing: schema/bootstrap, Keeper polling/classification, rate gate, Discord leadership, normal Discord status, Rich Presence, lifecycle behavior, logs, and operator health.
8. If healthy, restore the remaining fleet progressively rather than all at once.
9. Soak the backend for at least the complete 72-hour lifecycle; preferably approximately one week so console retired-probe behavior can also be observed.
10. Implement/update the public dashboard last.

Expected maintenance target is under approximately 30 minutes if validation is clean, but correctness/safe rollback takes priority over the target.

## Implementation order

1. Database/Alembic lifecycle foundation and name-history schema.
2. Formal Keeper result classification and conservative snapshot validation.
3. Central transactional lifecycle transition engine with out-of-order observation protection.
4. Change Keeper polling universe from guild associations to lifecycle-eligible global `bf4_servers`, preserving FAST/BULK priority semantics.
5. Discord lifecycle reconciliation and durable lifecycle message state.
6. `/addserver` and `/delserver` semantics.
7. Daily BFLIST PC discovery at 09:30 HST, owned by Discord leader.
8. CONFIRMED-only Rich Presence/live population aggregation.
9. Automated/static tests for lifecycle boundaries, failures, races, multiple guilds, resurrection, and console weekly probes.
10. Controlled production maintenance rollout and soak.
11. Dashboard lifecycle/data-quality presentation last.

## Required lifecycle tests

At minimum cover:

- CONFIRMED + 404 => GRACE and first_404_at set once.
- GRACE + success => CONFIRMED and outage fields cleared.
- GRACE + 404 before 60 minutes => remain GRACE.
- GRACE + 404 after 60 minutes => STALE and hourly probe scheduled.
- STALE + generic Keeper error => remain STALE; no false retirement.
- STALE + success => CONFIRMED.
- STALE + 404 before 72 hours => remain STALE and reschedule hourly.
- STALE + generic error after 72 hours => remain STALE.
- STALE + definitive 404 after 72 hours => RETIRED.
- RETIRED PC => no routine probe.
- RETIRED console => approximately 7-day probe.
- RETIRED + success => CONFIRMED.
- DISCOVERED + success => CONFIRMED.
- DISCOVERED + 404 => GRACE.
- DISCOVERED + generic error => DISCOVERED.
- Out-of-order older 404 arriving after a newer success cannot overwrite CONFIRMED.
- Multiple guilds referencing one GUID all reconcile correctly from one global lifecycle transition.
- `/addserver` never declares CONFIRMED without Keeper success and never resets first_404_at merely by invocation.
- `/delserver` never deletes the global catalog row.
- Management role is pinged once on STALE entry only; never from `/logschannel`.
- Temporary ONLINE notice is removed on the first post-recovery map change.
- Rich Presence excludes DISCOVERED/GRACE/STALE/RETIRED and includes CONFIRMED only.
